# 技术架构与目录约定

## 运行层

- `GameState`：跨场景的最小状态，包含天数、阶段、资源和全局信号。
- `DayLoop`：按阶段驱动每日循环，负责阶段切换和结算顺序；当前 Demo 的固定规则已移入 `src/core/day_loop.gd`。
- `Rules`：纯规则函数，接收状态并返回结果，避免把数值规则写进界面节点。
- `EventLog`：记录玩家选择、即时突发、资源变化和夜间因果链。
- `SaveSystem`：把 `GameState` 和 `DayLoop` 序列化为版本化快照，负责保存和恢复，不由 UI 直接拼接存档字段。

## 2D 手机端基线

- 所有场景使用 2D 节点和 Control UI，不引入 3D 相机、网格或模型。
- 目标画布为横屏 1280×720，UI 使用锚点和容器，保证后续适配不同手机比例。
- 图册中的“侧视”和“斜 45 度俯视”先作为两种 2D 构图方式处理；Demo 阶段优先完成信息层级和交互，不绑定最终背景透视。
- 正式背景资源未提供前，只使用几何占位、纯色、渐变和临时图标；禁止直接把设计示例图当游戏背景。

## Godot 文件约定

- `scenes/` 放可复用场景；场景名使用小写英文和下划线，例如 `rest_stop.tscn`。
- `src/core/` 放状态和规则脚本；脚本使用 `snake_case.gd`。
- `src/ui/` 放界面脚本；界面只负责输入和展示，通过信号调用规则层。
- `data/` 放 `.tres` 或 `.json` 数据，不把 NPC 和路线的大量参数硬编码在 UI；当前 Demo 数据入口为 `data/demo_content.json`。
- `assets/`（后续创建）按 `art/`、`audio/`、`fonts/` 分组；原始大图保留在设计文档目录，游戏内只引用裁切后的资源。
- `tests/` 放可在无界面模式运行的规则测试；当前入口为 `tests/run_day_loop_test.gd`。

## 状态边界

阶段顺序固定为：`MORNING → ROUTE_SELECTION → TRAVEL → REST_STOP → CAMP_ACTION → NIGHT_SETTLEMENT`。结局检查在夜间结算后执行，满足条件时进入 `ENDING`。

第一版使用资源字典和简单数据类快速验证循环；当字段稳定后再迁移到 `Resource` 数据文件。NPC 日程、对话结果和涌现结算要通过结构化记录传递，避免 UI 直接修改多个系统的内部变量。

## 输入策略

产品基线是安卓横屏触控。开发期保留键鼠映射，方便桌面测试；游戏逻辑只监听动作名，不直接判断具体按键。触控按钮在 UI 层发出同名动作或调用同一命令函数。
